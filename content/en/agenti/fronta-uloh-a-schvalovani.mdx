This whole series rests on one sentence: **the agent may prepare anything, the last click stays yours.** This part is about how to turn that sentence into something that actually holds — because as a good resolution it lasts a week.

## Why an agreement does not work

Most people try it like this: they write “never send anything without my consent” into the agent's instructions and consider it solved.

It is not. A model has no reliable boundary between what is data and what is a command. When the agent, in the course of its work, comes across text written by someone else — an attachment, a web page, an email — that text can tell it what to do. And it will do it with your permissions. That is the core of the problem known as prompt injection, which according to security reviews from 2026 is still behind most failures of agentic systems in production.

Only one sensible rule follows from this: **the boundary has to be where the agent has no way of crossing it.** Not in an instruction, but in the fact that it lacks the login details, lacks the permission or lacks the network access.

A practical test for sorting things: **what does it cost to take it back?** Nothing → first quadrant. A minute → second. An apology → third. Money or reputation → fourth.

## The queue: the simplest solution that works

You do not need any platform. The folder you already have from the previous part is enough:

```
~/velin/
  ke-schvaleni/
  schvaleno/
  zamitnuto/
  archiv/
```

The agent writes **exclusively** to `ke-schvaleni/`. It has no access to sending. It has no key to the mailbox. When it is meant to prepare a reply to an email, it saves it as a file — along with a note saying who it should go to and why.

You then move the file to `schvaleno/`, and only that move triggers the sending. The sending is done by a different, dumb script that can do nothing but take a file and send it. That script does not read anyone else's text, so nobody can slip it anything.

This is the key architectural trick: **the smart part has no permissions, the permitted part is not smart.**

## What every queue item must contain

For approval to be quick and still deliberate, an item has to answer three questions at a glance:

1. **What happens after approval.** In one sentence. “An email will go to address X.”
2. **What the agent based it on.** Source, link, quotation. Without it you are approving blind.
3. **What is finished and what is a guess.** When the agent is not sure, it should say so.

If an item lacks these three things, change the agent's brief, not your habits. Approval where you cannot see what you are approving is worse than none — it gives a false sense of control.

## Approving from your phone

Combined with the Telegram bot from the first part of this track, an ordinary day looks like this:

- In the morning the bot sends a summary: **“3 items for approval.”**
- For each one, a brief description and the buttons **Approve / Reject / Edit**.
- Approval moves the file and triggers the sending.
- Rejection moves it to `zamitnuto/`, and the agent learns from it next time, because it reads the rejected items.

A crucial detail: **the buttons must be named after the consequence, not the action.** Not “OK”, but “Send to client”. The difference in the number of mistakes is enormous.

## When approval turns into rubber-stamping

This is the most common way a good system stops working. After a month you have thirty items a day, they all look fine and you approve them with one thumb without reading them. From that moment you do not have control, you have a ritual.

Three antidotes:

- **Limit the volume.** If there are too many items, the agent is doing things it should not be doing. Narrow the brief.
- **Random checks.** Once a week pick one approved item and go through it in depth. You will find out what is getting past you.
- **Different weights.** Let routine items go through in bulk, but those from the third quadrant should always require opening and reading.

## What to watch out for

- **The agent must not have login details for anything it is not meant to do on its own.** This is the only protection that still works after the thousandth task.
- **Rejecting must be as easy as approving.** When rejecting is harder, people approve.
- **Log who approved what and when.** Even if it is only you. In three months it will come in handy.
- **Deal with the case where nobody approves.** Items that have sat for a week should either disappear somewhere or send a reminder — otherwise your queue gets overgrown.
- **Do not let the agent near other people's text and near sending at the same time.** That is exactly the combination the last track of the series describes as the lethal trifecta.

## Pro tip

Before you entrust the agent with anything, run its brief past one question: **“what is the worst that happens if someone rewrites this instruction?”** If the answer is “it prepares a nonsensical draft”, you are fine. If the answer is “it sends nonsense to a client”, your boundary is in the wrong place.
